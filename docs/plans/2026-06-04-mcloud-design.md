## Problem Statement
传统线上办公的硬件配置有变化趋势，未来不需要高配的“手边”设备，而是会分离为更轻量便携的输入输出终端（MacBook Air、iPhone）加低功耗的“无头”（Headless）超级计算机节点（M-series Mac Mini/Mac Studio/ECS）。
如何在多计算节点间建立低功耗、稳定连接的无缝卸载环境，并将闲置二手苹果设备低成本服务器化，是数字工作者和程序员的关键诉求。

## Demand Evidence
- 用户对轻薄办公趋势的深入研判，以及计算被卸载到各司其职的边缘计算单元之必然性。
- 用户身边大量的二手闲置 Apple 硬件（如 M1 Mac Mini/MacBook），需要高性价比地将其转换为极低功耗的 Headless 服务节点，避免云主机（如 GPU/NPU）的高昂租赁费。

## Status Quo
- 目前的野生做法是用 Tailscale + SSH + 虚拟 HDMI 显卡插头，但存在极高管理心智：重启 FileVault 锁死网络、后台进程内存泄漏导致能耗剧增、缺乏统一控制面来优化 CPU/内存/功耗指标。

## Target User & Narrowest Wedge
- **Target User**: 远程/移动办公的数字工作者与开发者（手持 MacBook Air，闲置二手 Mac 放在家里作为低功耗计算节点）。
- **Narrowest Wedge**: 极简的本地 CLI 与运行在远程 Mac 上的 Rust 代理守护进程，通过 Tailscale SSH 连接，解决 headless 运行、电源优化和编译任务卸载。

## Technical Architecture & Core Mechanisms

### 1. 双向文件同步 (Bidirectional File Sync)
- **推送阶段 (Push)**: 本地客户端在运行远程任务前，调用 `rsync` 通过 Tailscale SSH 将代码的源文件差异增量同步至远程节点的对应工作区（`~/.mcloud/workspaces/<project-id>/`）。
- **缓存冲突规避**: 
  - 本地与远程必须独立进行缓存管理。本地构建缓存（如 Rust 的 `target/`，Node.js 的 `node_modules/`）被硬性列入 `rsync` 过滤表（`--exclude`），避免异构 CPU 架构（如 Intel 客户端对 ARM 算力节点）或工具链版本不一致引起的编译错误。
  - 远程节点使用其自身的本地目录进行构建缓存，并推荐集成远程端的 `sccache` 等工具。
- **拉取阶段 (Pull)**: 编译任务完成后，客户端自动触发逆向增量同步，将远程生成的目标产物（通过配置文件指定的输出目录或默认检测出的新文件）差量同步回本地客户端工作区。

### 2. 功耗与睡眠管理 (Sleep & Power Management)
- **规避深度睡眠悖论**: 由于进入深度休眠后 Tailscale 进程挂起，远程将无法直接连通。本设计显式配置为**“显示器关闭、但 CPU/网络持续在线”**。
- **配置实现**:
  - `sudo pmset -a displaysleep 10` （关闭显示器输出，防止 GPU/显示芯片耗电）。
  - `sudo pmset -a sleep 0` （系统不休眠）。
  - M 系列芯片在此状态下的闲置功耗仅为约 3.1W - 3.8W，与深度睡眠功耗非常接近，但可以保持 100% 网络即时唤醒。
  - 合盖保护与 Caffeinate：如果节点是旧 MacBook，运行 `sudo pmset -a disablesleep 1`，同时守护进程在执行编译任务期间，通过 Rust 调用 `caffeinate -dis` 命令或在 OS 层声明 `IOPMAssertionCreateWithName` 休眠断言，确保系统不会在合盖、低电量或高热量时进入系统级睡眠。

### 3. 任务生命周期、进程托管与断网容错 (Task Lifecycle & Disconnection)
- **无外部依赖托管**: 为了避免远程节点强依赖 `tmux`（macOS 未内置），`mcloud-agent` 使用 Rust 的原生进程管理和重定向机制。远程执行的命令会将 stdout 和 stderr 输出直接重定向至远程节点本地的日志文件（`~/.mcloud/tasks/<task-id>/output.log`）。
- **状态与退出码持久化**: 
  - 任务进程运行在后台，其退出码（Exit Code）在进程终止时被捕获并保存至状态文件 `~/.mcloud/tasks/<task-id>/exit_code`。
  - 即使本地 client 在编译时合盖或断网，任务依然正常进行。用户重连后，客户端可以通过 `mcloud logs` 读取输出，并读取状态文件以向本地操作系统返回相同的进程退出码，从而无缝兼容 IDE 链。

### 4. 权限分离、安全模型与 IPC (Privilege Separation & Secure IPC)
- **双层代理架构**:
  - **`mcloud-sysd` (Root 守护进程)**: 以 `root` 权限运行，通过系统 launchd 加载。只负责测量功耗数据（解析 `powermetrics`）、修改系统电源策略（调用 `pmset`）和执行计划内重启（`fdesetup authrestart`）。该进程不面向客户端网络开放。
  - **`mcloud-agent` (User 代理)**: 以普通用户身份运行，通过 Tailscale SSH 接收并执行编译命令。
- **安全 IPC 通信**:
  - `mcloud-agent` 需要获取功耗或控制重启时，通过 Unix Domain Socket 接口向 `mcloud-sysd` 发送结构化请求。
  - Socket 文件存放在 root 拥有的受保护目录中（例如 `/var/run/mcloud.sock`），文件权限被设为 `0600`。仅允许 root 和该受信任的普通用户组写入，彻底杜绝本地其他恶意普通用户利用 socket 提权。

## Constraints & Pain Points Mitigations
- **FileVault 与崩溃重启**: 重申 FileVault 磁盘加密在无人值守的 Headless 节点上的局限。计划内重启使用 `sudo fdesetup authrestart` 在 NVRAM 暂存解密密钥实现一键重启；但为了应对断电崩溃等非计划重启，本方案**强建议算力节点彻底关闭 FileVault** 以确保自动引导入系统和网络上线。
- **YAGNI (MVP 范围缩减)**: MVP 阶段彻底剔除 BetterDisplay 等 GPU 虚拟化和 NPU 推理优化逻辑，专注做好 **CPU/内存密集型（代码编译、测试套件）** 的纯 CLI 形式卸载，以简化架构难度。

## Premises
1. 网络组网直接基于 Tailscale / WireGuard 等成熟虚拟局域网技术，不自研网络穿透。
2. 产品核心价值在于解决 macOS Headless 运作中的功耗、内存管理、远程断电重启等“苹果服务器化特有摩擦力”。
3. 客户端分发采用 CLI 配合 Homebrew / macOS App 的轻量形态。

## Cross-Model Perspective
- **Steelman (Strongest Version)**: Repurposes idle, consumer-grade Apple Silicon devices into a low-power, headless server cluster. Zero-config, mesh-networked.
- **The Revealing Quote**: *"另外我还看到一种趋势是，我们的二手苹果设备会也来越多如何变成服务器模式以低功耗的方式运行也是一个问题。"* Focus specifically on "recycling/repurposing utility" for Apple hardware, resolving lid-closed sleep, GPU scheduler degradation, and pre-boot FileVault locks.
- **Wrong Premise & Counter-Evidence**: Resolving remote FileVault reboots via software is blocked because network/Tailscale does not start until *after* the FileVault password is typed at boot. Unplanned reboots will cause remote nodes to lose network connection.
- **48-Hour Prototype Plan**: Rust daemon for launchd, Tailscale API, client CLI `mcloud run "make build"`, memory watchdog. Skip GUI, FileVault bypass (document instead), and virtualization (run directly in host OS user space).

## Approaches Considered
### Approach A: 极简 SSH + Rust 代理守护进程 (Zero-Config CLI) [RECOMMENDED]
- **Summary**: 本地客户端 CLI `mcloud` 通过 Tailscale SSH 发送任务并使用 rsync 增量同步目录；远程算力节点通过 Rust 守护进程 `mcloud-agent` 配合双进程权限分离和 `pmset` 调优功耗。
- **Effort**: S (Human: ~2 days / CC: ~2 hours)
- **Risk**: Low
- **Pros**: 极其轻量，开发周期短，无复杂网络协议开销，内存占用极低（<5MB）。
- **Cons**: 缺少图形控制面，完全依赖命令行交互。

### Approach B: Web 仪表盘 + 统一 Rust 代理集群 (Agent-Server Control Plane)
- **Summary**: 主客代理架构，通过 Web 页面统一控制并展现算力节点的温度、内存泄漏和 `powermetrics` 功耗。
- **Effort**: L (Human: ~2 weeks / CC: ~4 hours)
- **Risk**: Medium
- **Pros**: 界面极其精美，对多节点（Mac + ECS）管理友好。
- **Cons**: 开发周期长，涉及鉴权、WebSocket 等同步复杂度。

## Recommended Approach
**Approach A** (SSH + Rust CLI/Daemon)。因为该方案开发周期短、无安全面扩张风险，且由于采用了 Rust，守护进程能在无 GC 开销下实现极低内存占用（<5MB），完美证明相较于其他重型方案的功耗和内存优势。

## Open Questions
- 如何精确测量算力卸载时的瞬时功耗？（可通过 Rust 解析 `powermetrics` 命令行输出中的 `CPU Power` / `GPU Power` 并输出为数值报告）。
- `rsync` 在特大文件夹（如超过 10GB 且有海量项目）下的增量扫描耗时，是否会影响编译的即时体验？（可通过在客户端实现监听机制进行文件流式热同步）。

## Success Criteria
- 远程 Mac 算力节点在闲置时，依靠我们的低功耗休眠和进程优化，功耗被压低至 3W 左右；
- 客户端通过 `mcloud run` 发送编译任务时，能够自动进行代码增量同步并后台托管执行，断网重连后能输出日志并抓回编译产物。

## Distribution Plan
- CLI 工具通过 Homebrew 仓库分发，算力节点使用 launchd 管理守护进程。
- 提供 `mcloud doctor` 诊断指令，一键检测本地与远程的 Tailscale 联通状态、SSH 证书有效性及电源偏好配置。

## Dependencies
- Tailscale 客户端的安装与认证；
- macOS 终端的系统事件发送权限。
